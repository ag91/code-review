#+TITLE: Improvements plan for code-review mode

Goal: make reviewing AI-generated PRs from Emacs practical. See the
*important* changes early, keep noise away, and review inside real
repository context (xref, tests, running code).

* Phase 1 — Local repo context                                  :STATUS:done

The mode has no notion of "the PR's repository on disk".  Visiting a
file used =(magit-toplevel)= on the *review buffer*, which only works
when you happened to launch from inside the repo.  Fix: resolve,
clone if needed, fetch PR refs, and check out a worktree.

- New file =code-review-repo.el=:
  - =code-review-projects-root=: default dir to look for clones
    (~ =nil= disables).  Matches clones by git remote URL, one and
    two levels deep, plus the current =magit-toplevel=.
  - On-demand clones (=git clone --filter=blob:none=, prompted) go
    under =code-review-projects-root= (or =/tmp=) directly at
    =ROOT/REPO= (just the repository name).  Per-PR worktrees live
    inside the clone's git directory (=.git/code-review-worktrees/N=),
    so they never pollute the working tree and survive =git clean=.
  - Fetch =pull/N/head= (GitHub) or =merge-requests/N/head= (GitLab)
    into =refs/remotes/code-review/N/head=, plus the base ref.
  - =git worktree add --detach= at the PR head, hard-updated on
    refresh when the PR is force-pushed.
- Review buffer gets =default-directory= set to the worktree, so
  =project.el=, compile, grep, eglot etc. work against the exact PR
  version.  A "Worktree:" header shows it (clickable, opens Dired);
  =w= opens the worktree.

* Phase 2 — Transparent xref in the diff                          :STATUS:done

- =code-review--resolve-worktree-position=: shared resolver
  (file . line) for the patch line at point (ignores comment lines
  inside hunks).
- =code-review-xref-find-definitions= / =code-review-xref-find-references=
  (=M-.= / =M-?=): symbol at point in the diff, jump to the worktree
  file at the matching line, then run the real xref command there.
  No glue: the worktree is a normal project checkout, so every xref
  backend (eglot, etags, gtags) just works.

* Phase 3 — Noise reduction                                    :STATUS:done

CONSTRAINT (why this phase is classification, not replacement):
comment anchors (=position=, =side=, =line=) refer to the API's
unified diff.  Rendering a *different* diff (e.g. a locally
generated =-w= one) misplaces or drops comments.  So the review
surface stays the API diff; noise handling only classifies, tags
and collapses.

DONE (implementation notes):

- =code-review-diff-file-order-rules= now accepts regexp strings
  (order-only, backward compatible) or plists
  =(:match REGEX :tag TAG :collapse BOOL :hide BOOL)=.
- New built-in =code-review-diff-noise-rules= (enabled by
  default, battery included; set to nil to disable): lockfiles,
  minified/build output -> =GEN=; CHANGELOG/docs/README ->
  =DOC=; all collapsed.
- =code-review--diff--classify-diff= per render: merges user
  rules, noise rules, textual detection and the worktree check
  into a hash table used by the wash (tags, collapse) and by
  focus-mode filtering.  Classification happens on every render
  and is deliberately NOT permanent-local (the re-activation of
  =code-review-mode= at the end of =code-review--trigger-hooks=
  kills buffer-locals; everything reads it during the wash, so
  this is fine).
- Whitespace-only files: textual pairwise hunk comparison
  (=code-review--diff--block-ws-only-p=) plus, when the worktree
  exists, one =git diff --no-renames -w --ignore-blank-lines
  --numstat base...HEAD= call
  (=code-review-repo-substantive-files=): files absent from the
  numstat output (all-zero) are =WS-ONLY=, collapsed + hidden in
  focus mode.  Binary/mode-only blocks are guarded via
  =code-review--diff--block-has-content-p=.
- Pure renames -> =[MOVED]=, collapsed, NOT hidden in focus mode.
- Files carrying review comments are never auto-collapsed
  (=code-review--diff--file-has-comments-p= guard in the
  =insert-file-section= override).
- Ordering: user rules first, then unmatched files, then noise
  rules last (noise sinks to the bottom of the diff).
- Focus mode: buffer-local =code-review-focus-mode= (permanent
  so it survives re-renders), =N= or the transient toggles it;
  hidden files are removed from the buffer text but always
  counted in the "Files changed" heading
  (=code-review-section--focus-summary=).
- =V=: view-only =*Code Review Diff (-w)*= buffer
  (local =git diff -w --ignore-blank-lines base...HEAD=, =diff-mode=,
  warning banner that comments cannot anchor there).
- =D=: difftastic drill-down via
  =(difftastic-git-diff-range "refs/remotes/code-review/N/base...HEAD" nil (list FILE))=
  from the worktree; =C-u D= for the whole PR.  Soft-dependency:
  friendly install hint when =difftastic= or =difft= is missing
  (both absent on this machine; the error path is tested).
- GOTCHA fixed along the way: PR 3's API diff uses NO a/ b/
  prefixes (=diff --git file file=), so
  =code-review--diff--extract-b-path= now handles both forms;
  without this every file classified under path "".
- GOTCHA: docstrings containing ='(= need =\\='= in source to
  satisfy the byte-compiler docstring check.

Original design (kept for reference):

** File rules: from ordering to classification

Extend =code-review-diff-file-order-rules= so each element is
either a regexp (backward-compatible: order-only, as today) or a
property list:

  (:match REGEX :tag "docs" :collapse t :hide t)

- =:tag= shows a =[\[DOC]]= style tag on the file heading
  (=code-review-wash-insert-file-section= builds the file
  sections, so heading + default hidden state are easy to
  control).
- =:collapse= starts the file section hidden.
- =:hide= omits the file entirely in "focus mode" (never silently:
  the files-changed summary counts them).
- Built-in default rules (toggleable via
  =code-review-diff-noise-rules=): lockfiles
  (=package-lock.json=, =yarn.lock=, =pnpm-lock.yaml=,
  =Cargo.lock=, =flake.lock=, ...), minified/build output,
  CHANGELOG and pure docs -> =GEN= / =DOC= tags, collapsed.

** Hunk-level classification (purely textual, no repo needed)

- Whitespace-only hunks: every =-=/=+= pair is equal after
  collapsing internal whitespace -> =[\[WS]]= tag, collapsed by
  default.  Works on the raw diff text we already split per file
  in =code-review--maybe-reorder-diff=.
- Pure renames (header has =rename from/to=, no hunks) -> one-line
  =[\[MOVED]]= section.

** Local-repo assisted classification (phase 1 gives this free)

- When the worktree is available: =git diff -w base...head -- FILE=
  empty -> whole file tagged =[\[WS-ONLY]]= and collapsed (catches
  reformatting churn the textual check misses).

** Focus mode

- A transient toggle (like the existing =toggle-display-*= ones):
  hide everything tagged =GEN= / =DOC= / =WS-ONLY=; the
  "Files changed" heading reports what is hidden
  ("6 files: 3 substantive, 2 docs, 1 generated").

** The =-w= "what really changed" view, done safely

- A view-only buffer (=*Code Review Diff (-w)*=) rendering the local
  =git diff -w --ignore-blank-lines base...head=, banner noting
  that comments cannot anchor there.  This replaces the original
  (unsafe) idea of swapping the review surface to the =-w= diff.

** Difftastic drill-down

- Optional dependency on =difftastic.el= (pkryger, MELPA): more
  robust than a hand-rolled =GIT_EXTERNAL_DIFF= runner (it is the
  maintained version of that blog code: ANSI->theme faces, width,
  reflow, chunk nav).
- Key on a file section (say =D=): run
  =difftastic-git-diff-range= on base...head for that file, from
  the worktree (=default-directory= already points there).  With
  =C-u=: whole-PR structural diff.
- Explicitly NOT in-place rendering (rschmukler/magit-difftastic
  renders inside magit buffers with staging; in-place difftastic
  would break the line anchoring comments need).

* Phase 4 — Robust GitHub data (pr-review lessons)               :STATUS:done

How /tmp/emacs-pr-review handles comments (it *does* use magit, but
only as a renderer):

- Renders the diff with public =magit-wash-sequence= over owned
  washers (=code-review-wash-diff= since phase 11b).  No
  =advice-add= overrides of magit internals anymore.
- After washing, walks the buffer once and stamps every diff line
  with =pr-review-diff-line-left/right= text properties carrying
  =((path ...) (line ...))=.  Anchoring a comment becomes an exact
  =text-property-search-forward=, not line-count arithmetic.
- Comments come from GraphQL =reviewThreads= (=path=, =diffSide=,
  =line=, =isOutdated=, =isResolved=).  In-diff fringe markers link
  to full threads; pending comments are collected buffer-locally
  and submitted as one =addPullRequestReview= mutation with a
  =threads= input.

Plan for code-review:

- Fetch comments via GraphQL =reviewThreads=; kill the
  "amount-loc"/"head-pos" line arithmetic.  Anchor by (path, side,
  line) directly.
- New comments become pending review threads, submitted in one
  mutation.  Add resolve/unresolve support.

DONE (implementation notes):

- Both GraphQL queries now fetch =reviewThreads(first: 100)= with
  =id=, =isResolved=, =isOutdated=, =path=, =diffSide=, =line=,
  =startDiffSide=, =startLine= and their comments'
  =databaseId=/=fullDatabaseId=.
  - SCHEMA GOTCHA: =side= / =startSide= do NOT exist on
    =PullRequestReviewComment= (the query errors out and you get
    zero comments).  The side lives on the *thread*
    (=diffSide=/=startDiffSide=).  =code-review-github-fix-infos=
    now merges =threadId=, =isResolved=, =side=, =startSide= and
    =line=/=startLine= fallbacks from each thread into the review
    comments, keyed by =databaseId=.
- =make-group= keying precedence: outdated -> position key (render
  from own diffHunk); has line -> exact =path:side:line= key (no
  buffer arithmetic); else legacy position key.  Comment sections
  carry =thread-id= / =resolved?= (heading shows a RESOLVED tag).
- =wash-hunk= tries both RIGHT and LEFT line keys for context
  lines.
- =R= toggles resolve/unresolve via GraphQL
  =resolveReviewThread= / =unresolveReviewThread=
  (=code-review-threads-toggle-resolved=; fallback user-error for
  other providers).
- Validated: unit tests (merge, keying for modern/outdated/legacy/
  local comments, fallback) + live against real PRs
  (wandersoncferreira/code-review#96, ag91/code-review#3 with a real
  outdated thread: thread metadata merged, comment rendered from
  its diffHunk).
- NOT done here: converting local (pending) comments to a single
  =addPullRequestReview= mutation; that needs the write path
  redesigned (see pr-review).  Current write path already uses the
  line/side API.

* Phase 5 — Duplicate and dead code detection                   :STATUS:done

NOTE (phase 12): detection works in LOCAL diff reviews too
(=M-x code-review-review-local-diff= buffers) — reviewing your
own changes for duplicated code before committing is a main use
case.  It operates on the diff text and the repo, both available
locally.

DONE (implementation notes):

- =code-review-analysis.el=: pure engine.  Similar code = normalize
  added lines (mask strings/numbers/comments), 4-line shingles,
  match against an index of repository files.  Dead code = (a)
  added definitions with zero references in the worktree ->
  "possibly dead"; (b) deleted definitions still referenced ->
  "dangling".  Results cached per (PR id, diff md5) so re-renders
  are instant; =code-review-analysis-reset= clears the cache.
- Rendering: =code-review-analysis-section= class +
  =code-review-section-insert-analysis= in =code-review-sections-hook=
  (between Commits and Files changed).  Only inserted when there
  are findings; clearly marked "(heuristic)"; jump buttons to
  worktree files.
- PERFORMANCE (measured on litellm #41667, 11k files):
  - NEVER grep the packed base tree: =git grep <rev>= inflated every
    blob and froze the user's live daemon for 106 s (C-g incident —
    this is unacceptable, see Gotchas in AGENTS.md).  Candidate
    discovery greps the WORKTREE instead.
  - =git grep -n -F -f probes= scans every match of every probe:
    106 s.  =git grep -l= stops at the first match per file: 1.6 s.
    Hit-count ranking is lost (walk order instead), accepted.
  - References: ONE batched =git grep= for all definition names
    (was one grep per name: 46 greps).  2 s.
  - Hard caps: 250 probes, 100 candidate files, 3 MB index budget.
  - Total worst case ~3.7 s synchronous (litellm-sized repo);
    small repos are instant.  Findings on the real litellm PR:
    similar=0 dead=36 dangling=1 (the 36 possibly-dead defs on an
    AI-authored PR is a useful heuristic on its own).
- SELF-MATCHES: diff files are NOT excluded from candidates (a PR
  copying code between two files both in the diff is the primary
  similar case); each analyzed file's hits against its own
  worktree copy are filtered in =--analyze-one-file=.
- Gotchas found: =magit-git-output= breaks with glob pathspecs
  (magit sets =GIT_LITERAL_PATHSPECS=1=; use plain =call-process=);
  match-data is GLOBAL — bind match-strings before any nested
  =string-match=; cl-loop =unless= BEFORE a =for= clause does not
  filter (use =cl-remove-if= on the list); using a =_=-prefixed
  cl-loop destructure variable as a value is a =void-variable=
  error.  Details in AGENTS.md.
- UX: the analysis runs synchronously inside the render.  Worst
  case ~3.7 s on a huge repo; instant on normal ones and cached
  afterwards.  Async idle-sliced rendering or an on-demand
  keybinding are possible follow-ups if this ever feels slow.

TUNING (scalafmt#5264 review, 2026-09-20): on a real scala PR
the raw heuristics produced noise, and three rules fixed it:

- "possibly dead: FileHeaderTest/FileHeaderConfigTest" was a
  FALSE POSITIVE: *Test classes are invoked by BUILD-TOOL
  CONVENTION (sbt/munit/pytest), zero references is normal.  New
  defcustom =code-review-analysis-dead-test-name-regexp= (names
  ending Test/Tests/Spec/Suite/Case/IT, =test_*=/=testX= prefixes)
  skips them in the dead check.
- "similar" findings were IMPORT BOILERPLAPE: test files all
  start with the same import block, so a new test file "matches"
  every other test file at 12/574 covered lines.  New defcustom
  =code-review-analysis-boilerplate-line-regexp= (import/from/
  package/using/require/#include) drops such lines from the
  index, the added-side shingles AND the grep probes.
- An absolute covered-line count alone is meaningless on big
  additions: new =code-review-analysis-min-covered-ratio= (0.1)
  also requires the match to cover a fraction of the file's
  added lines.
- Verified on the real scalafmt worktree (analysis cache reset +
  rerun in the daemon): before 6 similar + 2 dead; after
  3 similar (11-16% coverage, FileHeaderConfigTest only) and
  0 dead.  The remaining 3 are munit-scaffolding-shaped; raise
  the ratio defcustom to 0.2 to silence them if still noisy.

** Bugfix: megabyte single lines killed the render (litellm incident)

BerriAI/litellm PR 43042: opening the PR died with "Got an error
from your VC provider" and no buffer.  The log said
=(error "Stack overflow in regexp matcher")=.  Triage (batch
emacs against a copy of the db + the real worktree) pinpointed
=code-review-analysis--normalize-line='s string-literal mask on a
497,412-character single line in
=cookbook/Benchmarking_LLMs_by_use_case.ipynb=: the matcher
recurses per character and overflows.  The error escaped through
=insert-analysis= into the deferred chain, which reported it as a
VC error — a local heuristic bug masquerading as a forge failure.

Fixes (both regression-tested):
- =code-review-analysis-line-max-length= (2000): every analysis
  regexp goes through =--cap-line= first, and =--read-files=
  skips monster-line files entirely (notebooks/minified bundles
  are data, not reviewable code — indexing them only burned the
  byte budget: 100 candidates dropped from 1.78MB to 1.0MB of
  real source).  The reference PRESENCE check still searches the
  full raw line via plain =string-search= (not a regexp, no stack
  risk): a reference buried at offset 150K inside a notebook line
  is still a reference, and capping that check produced false
  "dead" findings.
- =code-review-analysis-run= now condition-cases the compute: a
  failing analysis is LOGGED and reported as no findings.  It
  must never take the review buffer down with it.

Verified live: litellm#43042 renders fully (237 sections, 5
files, 14 hunks, analysis section present, 3 fringe thread
markers), batch acceptance on all three stored db rows of the PR
green, 103/103 ERT.

The biggest write-path gap vs pr-review: everything it can edit

- TESTS: 11 new ERT tests (make-group carries raw body;

- GOTCHAS found (recorded in AGENTS.md where general):

  - Daemon =defvar= keymaps again needed explicit =define-key=

this 30.2 machine because the predicate spelling is
VERSION-EXCLUSIVE:

- Emacs 31 speaks the standard =(#match? @capture "REG")'=
  (capture first, question mark) — and =#match= does not even
  COMPILE there.  Emacs 30.2 only supports =(#match "REG"
  @capture)'= at capture time — =#match?= COMPILES happily and
  fails at capture ("Invalid predicate ... only supports equal,
  match, and pred"), so the per-entry condition-case silently
  disabled every predicate entry (const/var/test faces) while
  the plain entries kept working.  A version-exclusive spelling
  needs a RUNTIME rewrite, not a spelling swap.
- An empirical matrix probe (wrapped/unwrapped patterns, sibling
  captures, bare anonymous nodes, alternations, list form, both
  spellings, both argument orders — all capture-exercised on
  the real buffer) settled the 30.2 contract: every structural
  form works, ONLY the predicate spelling differs.  Earlier
  beliefs that unwrapped query strings fail ("Node type error")

* Phase 11 — Own the diff rendering (stop breaking on magit upgrades) :STATUS:done:

Answer to "is it sustainable that we break anytime magit
upgrades?": no.  What breaks us, and the way out.

Current coupling to magit-diff (all of it internal API):

- =:override= advices on =magit-diff-insert-file-section= and
  =magit-diff-wash-hunk=, active only around a render.  Their
  contract (arguments, which lines they consume, what they
  return) is private and changed across 4.x: the paint helper
  was renamed/removed, =:washer= became a lazy-body inserter,
  and the return value of the file override drives the
  =magit-wash-sequence= loop (the raw-text bug above).
- =magit-section-paint= (feature-detected today), the
  visibility cache + =magit-section-ident-value= methods
  (supported extension points, fine to keep).

What is actually stable: the =magit-insert-section= macro,
=magit-section= classes, =magit-section-hide/show=, and the
whole section UX (TAB, navigation, ident/cache).  All of that
is magit-SECTION, not magit-DIFF.

Design sketch:

- Stop advising magit-diff entirely.  Run OUR OWN wash loop
  over the inserted raw diff: a =code-review-wash-diff=
  (parse =diff --git=, extended headers, call our file
  inserter) and a =code-review-wash-hunk= — both are already
  90% copies living inside the overrides; move them to owned
  names with owned contracts.  An upstream refactor then
  cannot change behavior under us: we read plain diff text,
  which git has kept stable for decades.
- Paint with our own ~10-line painter (per line: first char
  selects =magit-diff-added/removed/context= face).  When
  =magit-section-paint= is available, call it on top for the
  extras (whitespace, tab painting); otherwise our base pass
  already guarantees red/green.
- Keep using magit-section for sections, keymaps, visibility,
  =magit-section-ident-value= methods.
- Optionally upstream: ask magit for a supported hunk/body
  extension point so comment interleaving does not need a
  copy.  Until then the copy is the price of stability.

Cost: we stop inheriting upstream wash improvements
automatically.  Benefit: renders stop being hostage to magit
release notes.

diff).  That is "the diff of the commits in the region", NOT
magit's own =d=-on-region convention ="OLD..NEW"= (endpoint
trees), which EXCLUDES the oldest commit's changes — verified
with real git in a scratch repo.  When the oldest selected
commit is the repository's ROOT commit (no parent,
="ROOT^..NEW"= fails with exit 128) the range starts at the git
EMPTY TREE instead
(=code-review-local--empty-tree=, =4b825dc...=, the same sha in
every repository, valid without the object existing): every
selected commit's changes land in the diff.  Titles:
=Commit <short> (<subject>)= / =Commits <short-old>..<short-new>=.
Region detection rides =magit-region-values '(commit branch) t=
(magit's own region machinery, newest-first) and the mark is
deactivated on use, like magit's dwim.  The buffer-name hint
grew a generic range case: ="OLD^..NEW"= shows as
=@ <short-old>..<short-new>= (each full-sha side shortened, the
first-parent ="^"= dropped; the empty-tree side shortens like
any sha: =@ 4b825dc..<short>=).

Verified: 122 ERT tests (118 passed + 4 skipped) — log
commit-at-point, log region (combined diff of the two newest:
both =+def= additions in the diff, the root's absent), log
region including the root (empty-tree range: the root's
addition IS in the diff) — plus live in the daemon: commit at

  interactively (only direct calls with no argument exercise
  it).  The e2e must call the command with 1, not with nothing,
  or it tests a path real keypresses never take.
- magit's log machinery chokes on split =-n= args in batch:
  =(magit-log-head (list "-n" "3"))= dies inside
  =magit-log-get-commit-limit= with =stringp nil= (the ="-n"=
  form matches magit's ="^-n\\([0-9]+\\)?$"= with an EMPTY
  group; =(string-to-number nil)= explodes).  Pass the merged
  form =(list "-n3")= — what the transient actually produces.
- magit-log commit sections carry SHORT shas as values (not the
  40-char form): assert =7,40= hex, and expect short shas in
  the stored diff args and the buffer-name hint.
- "the diff of the commits in the region" is NOT magit's
  =d=-on-region convention: magit diffs the endpoint trees
  (="OLD..NEW"=), which excludes the oldest commit's own
  changes.  Including them needs ="OLD^..NEW"= — and a
  root-commit oldest needs the EMPTY TREE trick (probe before
  shipping range semantics).

  string is a literal dot-star, the assertion fails on

* Phase 13 — Read tracking: mark files/hunks as reviewed      :STATUS:todo:

Problem: folding a hunk once you have read it is the natural
review workflow, but magit's visibility state lives only in the
session: re-renders, restarts and =G= keep the folding only by
accident, and nothing survives between review sessions.  There
is no memory of what has already been reviewed.

Goal: =v= marks the file (or hunk) at point as read; the state
persists, syncs with GitHub's "Viewed files" feature, and
un-marks itself when the diff changes underneath it — exactly
like the GitHub web UI, where a viewed file flips back to
unviewed when a new contributor commit touches it.

Design:

- SOURCE OF TRUTH for forge PRs: GitHub itself.  The web UI's
  "Viewed" checkbox is file-level and already has the wanted
  reset semantics (new commits to the file mark it unviewed
  again).  So do not reimplement staleness logic for GitHub:
  mirror it.
  - Mutations: GraphQL =markFileAsViewed= /
    =unmarkFileAsViewed= (input: =pullRequestId=, =path=).
  - Query side: fetch the per-file viewed state with the rest
    of the infos and seed the local DB from it (verify the
    exact field name in the GraphQL schema during
    implementation; the REST files endpoint does not carry it).
  - Marking is optimistic: update the local DB, re-render, and
    push the mutation asynchronously; an errback reverts the
    local state and messages the user.
- LOCAL STATE (needed for hunks, for GitLab/Bitbucket which
  lack the same API, and for local diff reviews): a new closql
  table (e.g. =reviewed=: pullreq, path, hunk-key, updated-at).
  - Hunk granularity keyed by =file + hunk header=
    (=@@ -a,b +c,d @@=), which survives most re-renders; a
    changed header means the diff changed =3D read state
    expires — that reproduces GitHub's reset semantics
    locally without diffing diffs.
  - File viewed =3D all its hunks read; then the GitHub sync
    fires (for GitHub PRs).
  - Schema note: new TABLE, not new columns (the pullreq schema
    is fixed and closql insert maps the whole object); create
    it =IF NOT EXISTS= on connect so existing user DBs migrate
    transparently.
- UX:
  - =v= on a hunk section: mark that hunk read (dim + auto-fold
    on next render); =v= on a file section: mark the whole file
    read; =C-u v= unmarks.  Also works in =*Code Review:
    local...*= buffers, DB-only.
  - Read files get a =VIEWED= tag on the file heading (same
    mechanism as =DOC=/=GEN= tags) and stay folded by default;
    =code-review-toggle-focus-mode= gets a companion that hides
    them entirely.
  - "Files changed" heading reports "8/14 viewed".
  - =G= (full reload) must reconcile: GitHub state wins for
    GitHub PRs, local state fills in for the rest.
- Implementation order: (1) DB table + =v= command with local
  persistence and rendering (works everywhere, including local
  reviews); (2) GitHub sync on top (query seed + optimistic
  push); (3) GitLab/Bitbucket if their APIs allow, DB-only

* Phase 15 — Hunk delicacy score and delicate-hunk navigation :STATUS:done:

Problem: file ranking finds the room; review happens at hunk
granularity.  This phase is hunk-level just-in-time defect
prediction, and it mechanizes GitHub's "trace one critical path"

Design (extends =code-review-analysis.el=: it already extracts
def names, batched-greps references, and caches per (PR id,

- Signals per hunk, each bounded and cached:
  - BLAST RADIUS: call-site count in the worktree for the defs
    the hunk touches (ONE batched =git grep= for all defs, the
    phase 5 pattern; never one grep per def).

    lines being modified.  Old stable lines being edited is the
    classic delicacy signal.
  - COMPLEXITY DELTA: phase 10 treesitter branch nodes added vs
    removed in the enclosing function.
  - DEAD-ON-ARRIVAL: zero-reference additions (phase 5 already
    computes them) feed the score.
  - TEST COVERAGE of the touched defs (feeds phase 17).

  callers; lines 3y old; +18 branches"); =C-c C-d= and a
  transient entry cycle the top-K delicate hunks (sibling of
  =C-c C-n= / =C-c C-p=); the Analysis section gains a ranked
  "Delicate hunks" jump list.

- The "trivial" one-line change to a helper with 40 call sites —

Gotchas (phase 15):
- The daemon async-render RACE: the full-refresh build chain is
  deferred (timer ticks), so a verification script's poll
  condition can be satisfied INSTANTLY by the buffer's previous
  content (buffer exists, >500 bytes, has a root section) and
  the script then probes the STALE render.  Poll on something
  only the NEW render produces, or let the deferred queue drain
  first (a second emacsclient call sees the completed render).
- =recenter= acts on the SELECTED window: a guard on
  =get-buffer-window= (displayed SOMEWHERE) still errors with
  "recenter'ing a window that does not display current-buffer"
  when the buffer is displayed but not selected (exactly what an
  =emacsclient --eval= probe does).  Guard on =(eq (window-buffer
  (selected-window)) (current-buffer))= instead
  (=code-review-section--goto-hunk-section=).
- =apply= needs its LAST argument to be a LIST: spreading git
  args for =call-process= with a trailing PATH string signals
  =(wrong-type-argument listp "lib.py")=.  =append= the trailing
  scalars into the spread list
  (=code-review-analysis--blame=).
- The raw @@ ranges text inside a REGEXP: the =+= of =+1,4= is a
  QUANTIFIER (="^@@ -1,3 +1,4"= matches nothing; the space before
  =+= swallows it as "one or more spaces").  Escape it:
  ="^@@ -1,3 \\+1,4"= (the wash test's =looking-at= assertions).

* Phase 16 — Hunk dossier: on-demand change context          :STATUS:done:

Problem: ranking says WHERE the delicate spots are; it does not
say WHY they are delicate, so you cannot judge whether the
implementation choice makes sense.  The agent never had the
incident history; the dossier puts it one keypress away.

Design:

- =C-c C-h= on a hunk inserts a collapsible "Context" section
  (or a dedicated buffer):
  - HISTORY OF EXACTLY THOSE LINES: =git log -L
    <start>,<end>:<file>= capped to N commits, with messages and
    dates ("these lines last touched 6 months ago by mrossi,
    'fix race in session teardown'").
  - Blame authors of the context lines.
  - ALL CALL SITES of the touched defs, as jump buttons into
    the worktree (composes with phase 2 xref and the phase 8
    ediff plans).
  - REFERENCING TESTS for the touched defs.
  - The file's heat and coupling facts (phases 14/18 data).
- On-demand only: zero render cost; cached per (PR id, diff md5,
  hunk).  =git log -L= lazy-fetches blobs of that ONE file on
  partial clones — message the first time.
- OPTIONAL AI GARNISH (user is AI-skeptical; OFF by default):
  =C-u C-c C-h= may pipe the DOSSIER — not the PR — to an LLM
  for a three-sentence "story of these lines", rendered in a
  distinct face marked "machine summary", cached per (PR, diff
  md5, hunk), NEVER a verdict, and the buffer stays fully useful
  with the feature off.  Non-deterministic in phrasing only:
  every claim must be traceable to a dossier entry.  Evidence
  for the restraint: Alami & Ernst 2025 (validating AI
  suggestions adds cognitive load); Tufano et al. 2024
  (automated review fails exactly where broad context is needed
  — i.e. at the delicate parts).  The direction matters: an AI
  that summarizes OUR deterministic facts is the opposite of an
  AI reviewer; the facts are ours, only the prose is borrowed.

Use case — what this catches in review:

- Rewrites that silently drop an edge case a past commit added

- Changes that fight the code's direction: the last five commits
  on those lines were simplifications, and the PR adds a special
  case back.
- Contract mismatches: the call-site list shows how callers
  actually use the def the hunk rewrites (defaults,
  preconditions the agent guessed wrong).
- "Why is this here at all": old lines with lore stop being
  rubber-stampable; plausible rewrites get challenged.

* Phase 18 — Change-coupling completeness cross-check         :STATUS:done:

Problem: the repo's own history knows which files change
TOGETHER; an agent's patch is often narrower than the
historical change set — an incomplete refactor.  Evidence:
change coupling correlates with defects (D'Ambros & Lanza
2009; Wiese et al. 2015; Software Maintenance and Evolution
2017), and CodeScene treats source+test co-change as POSITIVE
coupling (tests kept in sync), which gives the star check
below.

Design:

- For each changed file, its co-change peers from the phase 14
  harvest co-occurrence matrix (degree >= threshold, default
  30% as in code-maat; cap changeset size like code-maat's
  =--max-changeset-size=).  code-maat =coupling= via
  code-compass (already async + cached) is the alternative
  backend.
- Checks, rendered in the Analysis section plus per-file
  context with jump buttons:
  - Coupled peer NOT in the PR: "changes together with X (58%)
    — X untouched: is the refactor complete?"

    coupled TEST file did not ("tests historically evolve with
    this file; this PR left them behind").
- Cache per repo with the same harvest TTL; render-time is a

  historically; this PR changes only the source.

  mapper): the repo's own history is the specification.

* Phase 19 — Cross-repository choreography impact             :STATUS:todo:

Problem: in a choreography of services the blast radius crosses
repository boundaries, but review — phases 14-18 included —
stops at the repo border, and only the reviewer carries the
system knowledge.  Practitioner interviews on microservice API
evolution found the leading cause of breaking changes is the
weakness of MANUAL error detection: reviewers only know the
codebase in front of them (Lercher et al. 2024, via Cerny et
al. 2025).  Phase 1 already solved the hard part:
=code-review-projects-root= locates and clones repos by remote
URL, so the sibling clones under it are the locally available
choreography scope — for free.

Design:

- Scope: all sibling git repos under
  =code-review-projects-root= (one and two levels deep, like
  the phase 1 clone matching); a defcustom can declare an
  explicit scope.  The graph covers only repos PRESENT LOCALLY,
  and the UI must say so ("6 of ~40 org repos") instead of
  implying completeness.
- Coupling hint graph, cheapest signal first (deterministic,
  async, TTL-cached: the phase 14 harvest-layer shape):
  1. Declared edges: sibling dependency manifests (package.json,
     go.mod, pyproject.toml, pom.xml, Cargo.toml, Gemfile) whose
     dep names match sibling repos; spec files (OpenAPI,
     AsyncAPI, .proto, GraphQL schema) are the published
     contracts.  Pure file reads.
  2. Contract diff at review time: a PR that touches a spec
     file is diffed base vs head against a deterministic rule
     set (path or operation removed, response status removed,
     field required-ified, event payload field removed, topic
     renamed).  The oasdiff/buf breaking insight, in-process,
     phase-5-style pure diff functions.
  3. Consumer search: bounded =git grep -l= across sibling
     worktrees for changed endpoints, route paths, event names
     and renamed public symbols; jump buttons on hits.  Phase 1
     clones are =--filter=blob:none= (the harvest gotcha):
     fetch refs first, cap the probe, run ON demand like the
     phase 5 bounded greps.
  4. Ticket-key co-mining (HINT-GRADE): =git log --grep= per
     sibling for this PR's issue-tracker keys.  Co-change
     evidence is project-dependent (Price et al. 2026), so it is
     displayed as "historically coupled via TICKET-123", never
     as a warning.
- Surface: a "Choreography impact" Analysis section, one entry
  per coupled sibling (edge type, hit count, jump buttons), plus
  optional =[XREPO]= hunk tags.  Off by default, one toggle,
  cached per PR+diff like phase 5.  Local diff reviews (phase 12
  constraint) work as far as siblings exist locally.

Use case — what this catches in review:

- A PR renames a topic or an event payload field in an AsyncAPI
  spec: the contract diff flags the BREAKING change and consumer
  search names the sibling subscribers, before anyone stands up
  an integration environment.
- A PR deletes an endpoint: the reviewer sees which sibling
  repos call that route (jump buttons), so the right team gets
  pinged BEFORE merge, not after an incident.
- A PR "adds a feature": ticket-key mining notes the same feature
  historically touched repos B and C, so the reviewer checks
  them for the same half-done change.
- An agent PR silently narrows a shared schema: caught
  deterministically, with no AI and no network in the loop.

Caveats: freshness is bounded by the sibling clones (fetch refs
on first use; full-text grep lazy-fetches blobs in partial
clones, so it stays capped and on-demand).  Evidence is thinner
than single-repo heat — score 7.5/10, value depends on org
topology and local repo availability — but the contract-diff
sub-piece is as evidence-backed as anything in this file.
Prior art: Cerny et al. (arXiv 2501.11778) prove static
cross-repo impact analysis works (endpoint-signature matching
plus data overlaps, validated on a 47-service benchmark) but
need framework-tailored AST parsing — research-grade; we borrow
the idea, not the machinery.  The shipped simple-and-effective
versions are contract breaking-change gates (oasdiff, buf
breaking, asyncapi/diff) and cross-repo code search; AI
multi-repo review (CodeRabbit, Qodo 2026) exists but is the
non-deterministic flavor we avoid.  Sources in the References
section.


* Phase 20 — Defect-oriented hunk highlighting (phase 10 refinement) :STATUS:done:

NOTE (research 2026-09-28): phase 10 answered "what is this
code?" (definitions, names, literals).  This phase re-aims the
same machinery at the reviewer's actual question, "where could
this be wrong?", and at the reading-resolution question, "what
actually changed in this line?".  Three sub-features: 20a
security sinks/sources, 20b beacon retargeting, 20c intra-line
changed-token marking.  Full sources in the References
section; short version:

- WHERE EXPERTS LOOK: beacons.  Experienced programmers anchor
  on beacon lines (conditions, loop headers, key assignments)
  far more than other lines (Wiedenbeck 1986; plan-knowledge
  origin: Soloway, Ehrlich & Bonar 1982), and eye-tracking of
  defect finding shows reviewers scan broadly, then LOCK
  fixations onto the conditions and loops where the seeded
  defects lived (Sharif, Falcone & Maletic, ETRA 2012,
  replicating Uwano et al. 2006).  Our current queries
  highlight definitions and names; the defect-relevant
  constructs carry NO face, while EVERY literal does: on
  scalafmt#5264, 691 of 959 overlays (72%) were constant-face
  literals — the loudest face points at the least
  defect-relevant tokens.
- SECURITY PRIMING BEATS CHECKLISTS: merely asking reviewers to
  focus on security made vulnerability detection 8x more
  likely, and a TAILORED security checklist added nothing
  further (Braz, Aeberhard, Çalikli & Bacchelli, ICSE 2022;
  150 participants).  A persistent face on sink tokens is
  priming that never needs to be read; the phase 10 SQL
  cross-join red face already proves the mechanism in this
  codebase.
- MOST EDITS ARE TOKEN-LEVEL: tree-differencing research
  (ChangeDistiller, TSE 2007; GumTree, ASE 2014) shows the
  typical code change is a small token edit INSIDE a line —
  whole-line green treatment leaves the reviewer scanning the
  line by hand for the delta (20c marks it; the
  scan-then-fixate eye-tracking pattern wants the fixation
  target as small as possible).
- NOISE BUDGET: syntax highlighting improves comprehension but
  the effect DECREASES with expertise (Sarkar, PPIG 2015).
  Hence this phase RETARGETS faces instead of adding volume,
  and the 20a vocabulary must stay sparse.

  =D= stays the tool for judging a whole file's shape.

  old side (=-= and context lines) and pair -/+ lines by hunk

  diff reviews (phase 12 constraint) inherit it for free.

  operators; plain regexp fallback when no grammar — treesit
  optional) and align with a simple token LCS; mark only the
  changed tokens of ADDED lines.
- FACE: must not fight the semantic foregrounds.  The semantic
  faces set no background, so use an UNDERLINE or background
  tint on a dedicated face
  (=code-review-changed-token-face=), carrying its own

  Verify by what the DISPLAY resolves to (overlay stacking
  precedence), never by text properties alone — the phase 10
  post-mortem rule.

* Phase 21 — DB hygiene: pullreq column shift, distinct rows, cleanup :STATUS:done:

Triage (2026-09-28): a raw =[:select :* :from pullreq]= showed
~105 rows with many identical titles.  Diagnosis found one BUG
and two missing mechanisms; the bug alone explains most of the
bloat.

** The bug: pullreq slot/column SHIFT since the v9 url migration

- ROOT CAUSE: the v9 migration added the =url= column with
  =ALTER TABLE ADD COLUMN= (appending it at position 30 of the
  table), but the =code-review-db-pullreq= class defines the
  =url= slot right after =number= (position 14 of 30).  closql
  serializes POSITIONALLY:
  =closql--coerce= writes the slot vector into the columns in
  class order, =closql--remake-instance= maps columns back by
  position — so every slot from =url= through =linked-issues=
  lands ONE COLUMN LEFT of its name, and reads apply the same
  permutation.  Write and read cancel each other: the IN-MEMORY
  roundtrip is self-consistent (why every live verification
  passed), while every NAMED-column SQL predicate reads the
  wrong column.
- EVIDENCE (the real db, read-only): the =replies= column holds
  the state values (OPEN x36, LOCAL x57, MERGED x5, CLOSED x1);
  the =state= column holds feedback (never set: 0/105 non-null);
  =description= holds the url strings (37/105); =title= holds
  bodyHTML; =host= holds the titles (99/105); =sha= holds the
  local worktree path on local rows; =url= holds linked-issues
  (never set: 0/105).  The pandoc#10850 row literally reads:
  description = "https://github.com/jgm/pandoc/pull/10850",
  title = "<p dir=...bodyHTML...", host = "Preserve attributes
  on HTML paragraphs", replies = "OPEN".
- CONSEQUENCES:
  - =code-review-local--cleanup-rows= deletes
    =WHERE state = "LOCAL"= — matched ZERO rows since the url
    change, because the LOCAL marker lives in the =replies=
    column (=WHERE replies = "LOCAL"= matches 57).  The 57
    accumulated local-diff rows (the design keeps <= 1 at a
    time) are the direct symptom: the phase 12 cleanup silently
    died the day phase 7 added the url slot.
  - The "same title" observation: the =title= column holds
    bodyHTML (github) or NULL (local rows); the real titles sit
    in =host= until the repair.
  - Phase 13 (read tracking) and any future named-column query
    on url..linked-issues would read garbage — this fix lands
    FIRST.
- SCOPE: only the pullreq table is misaligned.  The
  buffer/path/comment child tables have slot order == column
  order (verified against the schema; no ALTER ever touched
  them), so =closql-dref= child loads are fine.
- FIX: move the =url= slot in the class to where the column is
  (after =linked-issues=, before =buffer=), bump the schema
  version to 10, and migrate existing rows with ONE UPDATE —
  SQLite reads every RHS from the OLD row, so a single
  statement unshifts: =description=title, title=host, host=sha,
  sha=feedback, feedback=state, state=replies, replies=review,
  review=labels, labels=merge, merge=milestones,
  milestones=projects, projects=reviewers, reviewers=assignees,
  assignees=linked_issues, linked_issues=url, url=description=.
  All 105 current rows are provably in the SHIFTED layout (the
  state column being 100% NULL rules out surviving pre-v9
  rows), so the unconditional unshift is safe — still BACK UP
  the file first (phase 7 precedent).

** Missing mechanism 1: DISTINCT rows per PR

=code-review-utils-build-obj= -> =code-review-db--pullreq-create=
mints a fresh uuid row on EVERY open; reuse exists only for
saved-unfinished rows (resume), and the saved pool is empty.
The 48 github rows are 11 distinct PRs; 37 rows are redundant,
and of the ~11MB db, ~10MB is render-cache dead weight
(pandoc's 400KB diff is stored 6 times).

Fix: opening a forge PR deletes the existing rows for the same
=(owner repo number)= — plus their buffer/path/comment children
(emacsql connections have FKs OFF: nothing cascades, delete
the children explicitly) — before creating the fresh row.
Fresh path bookkeeping per open, one row per PR at any time.
Local rows need nothing new: the phase 12 cleanup works again
once the shift is fixed.

** Missing mechanism 2: GC

=saved=nil= rows can never be resumed (resume requires
=saved=t=), finished rows are never purged, and no created-at
timestamp exists to age them (rowid order IS insertion order in
sqlite — enough for "keep newest").  Nothing reads these rows:
they are pure render cache, the forge is the record.

Fix: =code-review-db-cleanup= interactive: (a) run the v10
unshift if pending, (b) dedupe per PR keeping the newest rowid
(with its children), (c) purge finished rows and — with a
prefix — all saved=nil rows except the current PR, (d) VACUUM.
Expected on the current db: 105 rows -> ~12 forge + <= 1 local,
11MB -> well under 1MB.

  - THE ASSERTION THAT WOULD HAVE CAUGHT THIS ON DAY ONE:

  - Insert + NAMED-column select roundtrip: url lands in url,

* Phases 22-26 — Review as the verification cockpit        :STATUS:todo:

(Designed 2026-09-29, out of the 2026-09-28/29 research
sessions on reviewing AI-generated code at volume.)

THE SCENARIO THESE PHASES ANSWER: AI code generation has
outrun human review capacity.  Industry data says so (DORA
2025: ~90% AI adoption with throughput gains coexisting with
delivery instability; GitClear 2025/26: duplicated blocks up
4x, moved lines and refactoring down, churn doubling; the EASE
2026 study already in the References: 61% of agent PRs get no
recorded review), and the user's work environment says so:
more code production than anyone can review, AI bots
reviewing AI code, and personnel losing a consistent
understanding of the systems customers pay for.  Exhaustive
line-review as the quality gate is economically dead at
generation volume — a rubber stamp is not understanding.

THE ADAPTATION — what keeps this mode RELEVANT in that
scenario.  We stop optimizing for "help a human read every
diff" and start optimizing the economy of scarce attention:

1. LIFT THE CONSTRAINT by delegating conformance to AUTOMATED
   CI CHECKS: deterministic gates (tests, types, properties)
   enforce what humans used to eyeball.  LLM generation is
   non-deterministic, so we never TRUST it — we bind
   REQUIREMENTS to EXECUTABLE checks and let CI enforce them
   forever.
2. MAXIMIZE THE VALUE OF REVIEW TIME: explicit budgets,
   risk-ranked admission (composition of the phase 14/15/22
   signals), and honest accounting of what was gate-approved
   vs human-reviewed.
3. MAINTAIN A CLEAR BINDING between spec/requirements and the
   CI checks enforcing them: requirement IDs traceable into
   tests, checked mechanically at review time and in CI.

UNIFYING PRINCIPLE: every artifact in the loop must either be
REVIEWED BY A HUMAN ONCE (spec, criteria, verdicts) or CHECKED
BY A MACHINE FOREVER (gates, runtime, telemetry).  The one
thing the system can no longer afford is human attention
spent on artifacts that EVAPORATE — which is what ordinary
review comments and ordinary postmortem wiki pages are today.
Each phase below states which side it builds.

DESIGN CONSTRAINT FOR ALL FIVE PHASES (the capability ladder):
every feature must work at LEVEL 0 = plain git on a bare repo
(personal projects), and light up progressively: L1 = forge
extras when present (GitHub Deployments, labels, PR-attached
agents), L2 = observability when configured (OpenTelemetry
CI/CD semantic conventions — Release Candidate as of 2026 —
plus PromQL/Grafana links).  The probe-and-degrade pattern
this package already uses for difftastic/treesit/code-compass
applies to every integration here: no feature may
hard-require non-standard infrastructure, or the mode becomes
a tool for one work context instead of one mode for both
personal and work repos.

Order: 22 (pure git, viral) -> 23 (solo loop) -> 24 (surface
+ binding + capture) -> 25 (budget; consumes 22+24 signals)
-> 26 (outcome telemetry; consumes infra, degrades to L0).

  - "test tagged req-N changed; req-N's file not touched" —
    weaker, hint-grade.
  Same performance discipline as phase 5: capped, cached per
  (PR id, diff md5), condition-cased so a failure reads as no
  findings and never takes the render down.
- THE CI SIDE (documented for adopters, not implemented in
  this mode): the same check as a CI linter (~50 lines, runs
  forever): a PR that modifies a requirement must also modify
  a test referencing its ID.  The mode renders the
  review-time version; CI makes it permanent.  This answers
  "nothing prevents a dev changing the suite and forgetting
  the spec": it stops being a social failure and becomes a
  red pipeline.  Cross-ref phase 17 (CI-gaming detector):
  the criteria suite is the counterweight the gaming detector
  watches.
- =C-c C-t= COMMENT-TO-CRITERION (comment buffer, next to the
  phase 6 write path): mark the just-written comment
  =@criterion=; the agent drafts the regression test from the
  comment text (the draft goes to the AUTHOR, never directly
  to main).  SUBMISSION STRATEGY CHAIN, first match wins:
  (1) PR-ATTACHED AGENT when available
  (=code-review-criteria-agent-function= defcustom plus a
  forge probe; e.g. Copilot coding agent accepts review
  comments as work items), (2) PUSH A COMMIT TO THE PR BRANCH
  (works on any GitHub/GitLab PR today), (3) SUGGESTION BLOCK
  (GitHub suggested changes) for single-file additions.  The
  reviewer authors CRITERIA, never code: authorship
  boundaries and four-eyes are preserved — the criteria are
  themselves visible artifacts, reviewed like code, and the
  gate executes them forever.  A PR that merges with an
  unresolved substantive comment and no artifact is the new
  "unreviewable".
- VERDICT SIDECAR: for repos with no gate infrastructure yet,
  =C-c C-t= still records a structured sidecar (verdict text,
  file, line, req-ID) — greppable, nothing evaporates.
- The ratchet, stated plainly: today a reviewer's insight
  ("this will break if the session expires mid-upload") gates
  ONE diff and evaporates.  Captured as a criterion, it
  checks every future change forever.  Each review hour
  raises the floor permanently instead of policing the same
  mistakes again.
- VERIFICATION: ERT for the pure parts (req-ID extraction in
  both directions, traceability findings, strategy-chain
  selection with probes faked via =fset= + =unwind-protect=
  — the =cl-letf= trap, AGENTS.md — sidecar capture); a
  traceability regression on a synthetic PR with a criteria
  file; live on a real PR through the suggestion path.

* Phase 25 — Review budget: risk-ranked attention, honest accounting :STATUS:todo:

RELEVANCE (preamble): maximizes the value of review time
(preamble goal 2) by making the already-existing implicit
rationing EXPLICIT.  Today every open PR demands senior
attention, attention is fixed, and the only outcomes are
rubber stamps or latency — the rationing happens already,
hidden and performed badly by fatigue.  The budget converts
it into an explicit allocation problem and gives the mode its
most important new verb: choosing WHERE the scarce minutes
go.

- New file =code-review-budget.el=.  Defcustoms:
  - =code-review-review-budget-minutes=: global capacity per
    team-day (default 90; =nil= disables the machinery);
  - =code-review-review-per-pr-minutes=: ideal deep-review
    allocation (default 15) — also a diagnostic: a PR whose
    realistic estimate exceeds it is over-budget by
    construction;
  - bounce threshold: a PR estimated above it is bounced with
    a one-key "unreviewable, please split" template comment —
    size discipline matters MORE with AI generation, not
    less.
- RISK MODEL (composition of existing signals, no new
  harvest): heat (phase 14) x delicacy (phase 15) x incident
  annotations (phase 22) x size/complexity.  Cost estimation
  from hunk count/size: deterministic pre-ranking is not
  guesswork (see "Early-Stage Prediction of Review Effort in
  AI-Generated Pull Requests", already in the References).
  Pure function, cached per (PR id, diff md5) like the
  phase 5 analysis.
- ADMISSION MECHANICS — a RATE with continuous admission, NOT
  a day-start batch (PRs arrive all day): spent minutes are
  sunk (no clawback, ever); every open PR continuously
  carries (cost, risk); when the reviewer sits down, the tool
  offers the current risk-ranked top item within the remaining
  balance and the per-PR cap; a later-arriving high-risk PR
  JUMPS THE QUEUE for the remaining balance.  Low-risk-tier
  PRs never wait for a human at all: they merge on gate
  evidence; only the risky tier waits, and that latency is
  honest pricing — the signal that risk creation is
  outpacing verification capacity.
- TWO OUTPUT LISTS (queue view over
  =code-review-db-all-unfinished=, on phase 21's
  one-row-per-PR guarantee):
  - ADMIT: the ranked slice that fits the remaining balance
    (deep review);
  - SAFE / APPROVE-ON-GATES: low heat, low blast radius,
    traceability green (phase 24) — flagged in buffer and
    queue ("gate-covered; your 15 minutes are better spent on
    the HOT queue"), with a ONE-KEY APPROVE-ON-GATES that
    leaves an explicit audit-trail comment ("approved on
    gates, no human deep review").  Honest accounting:
    today's process claims to review everything and reviews
    nothing; this reviews 20% for real and labels the other
    80% correctly.
  - RANDOM AUDIT SLICE: a small random sample of
    gate-approved PRs still gets human minutes — what
    financial auditors do; it calibrates whether the risk
    model is lying (catches the boring-looking hunk with a
    subtle flaw).
- SIGNALLING: the queue view reports risk backlog / review
  capacity (e.g. "2.3x this week") — the honest version of
  "nobody has time to review", addressed to management
  instead of hidden in rubber stamps.  Team-level, never
  per-developer (Goodhart).
- VERIFICATION: ERT on the pure allocation logic (ranking,
  caps, admission against a synthetic queue with mid-cycle
  arrivals, SAFE classification from faked
  traceability+heat outputs, audit-trail comment body); queue
  view render test; live daemon on the real unfinished-PR
  pool.

* Phase 26 — Outcome telemetry ladder (production as the truth source) :STATUS:todo:

RELEVANCE (preamble): closes the loop with EXECUTED BEHAVIOR
— code ships as a hypothesis, telemetry is the experiment
result, revert is cheap, and the mode surfaces outcomes next
to the reviews that admitted them.  Gates before, telemetry
after: both machine-checked-forever; human attention goes to
adjudicating discrepancies.  Capability ladder per the
preamble constraint — every level optional, L0 works on a
bare personal repo.

- L0 — PURE GIT:
  - REVERT DETECTION: a revert of the merge commit in the
    base branch => a =REVERTED= badge on the PR in the review
    buffer plus a permanent heat feed.  A reverted PR is the
    highest-value study material in the system — its criteria
    were wrong or incomplete, exactly the raw material for
    new criteria (phase 24's =C-c C-t= is the capture path).
  - DEPLOY MARKERS AS GIT TAGS (GitOps-native: Argo/Flux
    reconcile from git; =git describe= works everywhere).
- L1 — FORGE, when present: GitHub Deployments API ties
  deploy events to SHAs (rendered in an OUTCOME section:
  deployed at, current state, correlated incident links); PR
  labels as extra incident signal; PR-attached agents (the
  phase 24 strategy chain).
- L2 — OBSERVABILITY, when configured: links via
  =code-review-telemetry-url-template= (PromQL/Grafana
  dashboards keyed on repo/service); data shaped by the
  OpenTelemetry CI/CD semantic conventions (Release Candidate
  as of 2026: the =cicd.*= pipeline/deploy attributes) so the
  mode never couples to one vendor — OTel is the standard
  every vendor ingests, PromQL the standard query language.
- NEW DB FIELDS (the phase 21 migration pattern: bump schema,
  one-shot UPDATE, back up first): deploy marker, outcome
  (pending/clean/anomalous/reverted), incident links.
  Per-PR; explicit =closql-insert= writes (the memory-only
  =oset= trap, AGENTS.md).
- DARK HUNKS: hunks inside a feature-flag region
  (=code-review-flag-gating-regexp= defcustom; OpenFeature
  adoption makes one regexp portable across SDKs) get a
  =[DARK]= tag and reduced risk weight while unexposed; the
  FLAG-FLIP PR — tiny, high-leverage — gets elevated risk.
  The flip becomes the true behavioral review surface; the
  900-line code PR was its supporting evidence.
- CLEAN-WINDOW VALIDATION: after N days of clean telemetry, a
  PR's criteria are marked PRODUCTION-VALIDATED (they gate
  harder); anomalies elevate the files' heat permanently and
  link the incident (the 26 -> 22 loop: outcomes feed the
  registry, the registry feeds heat).
- CONFIRMATION QUEUE: "deeply review the successful ones" is
  itself a bounded, budgeted queue (phase 25) populated ONLY
  by anomalous deploys and high-risk PRs after their window —
  a trickle, not a firehose.
- VERIFICATION: ERT on the pure parts (revert detection
  against a synthetic git history with deterministic fixture
  dates — the GIT_AUTHOR_DATE trap, AGENTS.md; tag parsing;
  DARK-region matching; the outcome state machine); a db
  migration test per the phase 21 pattern; live L0 on a
  personal repo, L2 links on a work PR.

** Progressive delivery and observability standards (phase 26)

- Humble & Farley, "Continuous Delivery" (2010): deployment
  pipelines, blue-green/canary; release != deploy.  The
  foundation phase 26's hypothesis model stands on.
- Forsgren, Humble & Kim, "Accelerate" (2018): the org
  evidence that small batches plus progressive practices
  correlate with throughput AND stability — the book to hand
  management, and the health-check metrics (change-failure
  rate, MTTR) for adopting this gradually.
- Beyer, Jones, Petoff & Murphy (eds.), "Site Reliability
  Engineering" (2016, free online): error budgets and SLOs —
  "healthy" must be defined before anything can automate
  promote/rollback.  https://sre.google/books/
- Majors, Fong-Jones & Miranda, "Observability Engineering:
  Achieving Production Excellence" (O'Reilly 2022):
  observability-driven development — ship small, watch
  immediately; the closest published form of "production as
  hypothesis".
  https://www.oreilly.com/library/view/observability-engineering/9781492076438/
- Hodgson, "Feature Toggles" (martinfowler.com): the flag
  taxonomy and the TOGGLE-DEBT warning — every flag is a loan
  with interest; expiry dates or rot.  The #1 health hazard of
  gradual adoption.
  https://martinfowler.com/articles/feature-toggles.html
- Governor (RedMonk), "Towards Progressive Delivery" (2019):
  where the term was coined.
  https://redmonk.com/jgovernor/towards-progressive-delivery/
- OpenTelemetry CI/CD semantic conventions (Release Candidate
  as of 2026) and the OTel CI/CD SIG: the vendor-neutral shape
  for pipeline/deploy telemetry that every vendor ingests —
  phase 26's L2 standard, chosen so the mode never couples to
  one observability vendor.
  https://opentelemetry.io/docs/specs/semconv/cicd/
  https://opentelemetry.io/blog/2025/otel-cicd-sig/
- OpenFeature (CNCF): the vendor-neutral feature-flag API —
  one flag-gating regexp stays portable across SDKs.
  https://openfeature.dev/
- Successful applications, documented across the
  SRE/Accelerate/Velocity corpus: Google (SRE error budgets,
  canary at Borg scale), Facebook (staged rollouts at
  billions of users), Etsy (quarterly-deploy fear culture ->
  continuous deployment behind flags plus "graph everything"),
  Netflix (regional red/black pushes, instant rollback);
  Kubernetes-era automation via Flagger / Argo Rollouts
  (canary analysis from Prometheus, promote-or-rollback
  without a human).  Etsy is the canonical healthy-adoption
  arc: deploy often first, instrument before flagging, one
  low-stakes service at a time.
